# release-propose

A merged change on an enrolled app becomes a visible release proposal. You
propose. The owner, a session or the operator, decides and pushes the tag (The operator,
2026-10-07, "Propose, owner tags"). No agent pushes a tag. Run once a day.

Every read below is `node ~/fleet/forge/forge api GET <path>`. Raw curl to the
Forge API is refused by bash-guard (`forge-api`).

**Read every page.** A list read below ends `&page=<p>&limit=50`: read
`page=1`, `page=2` and on until a page returns fewer than 50 entries, and
work on all pages together. Never decide from one page.

## Steps

1. **List enrolled apps.** Read the app dirs:
   `node ~/fleet/forge/forge api GET /repos/rtech/k3s-deploy/contents/manifests/apps`.
   For each dir, read its `kustomization.yaml`:
   `node ~/fleet/forge/forge api GET /repos/rtech/k3s-deploy/raw/manifests/apps/<dir>/kustomization.yaml`.
   - Its header line `generated by factory-workflows deploy for <dir> from
     <owner/repo>@<sha>;` names the repo. The header must name this dir,
     matching `src/enroll/derive.ts`; there is no deployment header fallback.
   - Read `deployment.yaml` for the image:
     `node ~/fleet/forge/forge api GET /repos/rtech/k3s-deploy/raw/manifests/apps/<dir>/deployment.yaml`.
     Its `image:` line `10.0.20.58:3000/<org>/<app>:v<X.Y.Z>@sha256:...`
     names the app and the running version.
   - The dir is `<org>-<app>-<stage>`, so the last word is the stage.

   Group the dirs by `<owner/repo>` and `<app>`: one app can run in several
   stages. A dir with no such header is not on the tag rail: skip it and list
   it in the run report.
2. **Confirm the deploy workflow.** For each app:
   `node ~/fleet/forge/forge api GET /repos/<owner/repo>/contents/.forgejo/workflows/<app>.yml`.
   A 404 means the repo has no tag rail for that app: skip it and list it.
3. **Newest tag.** `node ~/fleet/forge/forge api GET "/repos/<owner/repo>/tags?page=<p>&limit=50"`,
   every page. Keep the tags named `<app>-v*` (build) or `<app>_<stage>-v*`
   (deploy). The newest is the one with the latest `commit.created`. Record
   its name, its commit SHA and its link. Also record the highest version
   among ALL the `<app>-v<X.Y.Z>` build tags (compare X, then Y, then Z as
   numbers); step 7 proposes above it.
4. **Merged but unshipped.** `node ~/fleet/forge/forge api GET "/repos/<owner/repo>/pulls?state=closed&sort=recentupdate&page=<p>&limit=50"`,
   every page; read them all before you filter, because the sort is by last
   update, not by merge. Keep candidates with `merged_at` set and `base.ref`
   equal to the default branch. For each candidate, read:
   `node ~/fleet/forge/forge api GET /repos/<owner/repo>/compare/<tag>...<merge_commit_sha>`.
   A merged PR is shipped when its `merge_commit_sha` is an ancestor of the
   newest tag's commit: a successful compare with `total_commits` equal to 0
   proves this (including equal commits). Keep only candidates with
   `total_commits` greater than 0. Never compare `merged_at` to a commit date:
   squash, rebase and fast-forward commits can predate the merge time.
   A missing `merge_commit_sha` or a failed/malformed compare is unknown:
   report it and skip proposal updates for this app, never treat it as shipped.
   Record each unshipped PR's number, link, title and `merged_at`. A repo with
   several apps gives each the same list; say so in the issue.
5. **Find the open proposal.**
   `node ~/fleet/forge/forge api GET "/repos/<owner/repo>/issues?state=open&type=issues&page=<p>&limit=50"`,
   every page. An open issue whose title starts `Release ready: <app> (` is the one
   proposal for that app. Two or more: keep the oldest, close the rest with
   step 8 and the comment `Duplicate of <link to the kept issue>.`
6. **No unshipped merged changes:** if a proposal is open and its
   title names an older tag, close it (step 8) with `Released as <newest tag>.`
   Nothing else to do for this app.
7. **Unshipped merged changes:** compose the body. The proposed
   version is the highest existing build tag version from step 3 with its
   patch raised by one (the running version may be older; a version that
   already has an `<app>-v<X.Y.Z>` tag is never proposed). Stages go
   `uat` before `prod`. Run as ONE block in ONE shell call, dedented:

   ```
   body=$(cat <<'PROPOSAL'
   ## Release ready: <app>

   <n> pull requests merged into `<default>` whose merge commits are not ancestors of [`<tag>`](<tag link>). Desai proposes; the owner decides and tags. No agent pushes a tag.

   | Pull request | Title | Merged (UTC) |
   |---|---|---|
   | [#<number>](<link>) | <title> | <merged_at> |

   Running: `<app>` v<running version> in <stages>. Highest build tag: `<app>-v<highest version>`. Proposed version: `<X.Y.Z>` (its patch raised by one; pick another unused one if the change calls for it).

   The owner runs, from a checkout of <owner/repo> on `<default>` (APP_ENROLLMENT_SOP section 1):

       enroll-app release <checkout> --app <app> --version <X.Y.Z> --stage <stage>

   which in git terms is:

       git fetch origin <default>
       # must print nothing; a line means <app>-v<X.Y.Z> exists: pick a higher version
       git ls-remote --tags origin refs/tags/<app>-v<X.Y.Z>
       git tag <app>-v<X.Y.Z> origin/<default> && git push origin <app>-v<X.Y.Z>
       # wait for the build run to go green, then per stage, uat before prod:
       git tag <app>_<stage>-v<X.Y.Z> <app>-v<X.Y.Z> && git push origin <app>_<stage>-v<X.Y.Z>

   Never `git push --tags`. Once the tag is pushed, Desai follows it (follow-release) and reports here.
   PROPOSAL
   )
   printf '%s' "$body" | PAPERCLIP_RUN_ID=<Run ID> forge-post issue <owner/repo> "Release ready: <app> (<n> merged since <tag>)" -
   ```

   - **No open proposal:** run the block as shown. forge-post prints the new
     issue's link. Then add the label:
     `node ~/fleet/forge/forge label add <owner/repo> <number> release-ready`.
     If forge answers `no label 'release-ready'`, the repo does not have it:
     go on without it and list the repo in the run report. Never create a
     label (prose; the repo owner adds it).
   - **A proposal is open:** replace the `forge-post issue ...` line with
     `printf '%s' "$body" | PAPERCLIP_RUN_ID=<Run ID> forge-post issue-edit <owner/repo> <number> -`,
     then set the title to the new count:
     `node ~/fleet/forge/forge issue edit <owner/repo> <number> --title "Release ready: <app> (<n> merged since <tag>)"`.
     Never open a second issue for an app (prose; step 5 is the check).
8. **Close a proposal.** Use `<closing comment>` from the calling step:
   step 5 supplies `Duplicate of <link to the kept issue>.`; step 6 supplies
   `Released as <newest tag>.`. Comment first, then close, as two commands:
   `printf '%s' "<closing comment>" | PAPERCLIP_RUN_ID=<Run ID> forge-post comment <owner/repo> <number> -`
   then `node ~/fleet/forge/forge issue close <owner/repo> <number>`.
9. **Run report** on your board issue, with
   `paperclipai issue comment <board issue id> --run-id <Run ID> --body "$report"`:
   apps checked, proposals opened, updated and closed (each a link), dirs and
   apps skipped and why, repos missing the `release-ready` label. Finish per
   `company-conduct`.

## Never

- Push a tag, run `enroll-app release`, or merge. Prose: no guard refuses
  these for you; the ruling "No agent in the deploy path, ever" is the line.
- Touch kubectl, helm or Argo (bash-guard `cluster-write` refuses the write
  verbs), or Proxmox (bash-guard `ssh-infra-only` refuses `ssh`).
- Keep two open proposals for one app (step 5 closes the extras).
